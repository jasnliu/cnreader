# Custom Test Listening Mode Design

## Objective

Add an optional Listening question type to the Words and Phrases Custom Test. A listening question plays a locally stored Mandarin recording, asks the learner to write the answer privately, and then reveals the character or phrase. Listening is strictly an honor-system activity: it does not record correctness, affect progress, add missed items, or change targeted-review knowledge.

All recordings use the same `zh-CN-XiaoxiaoNeural` voice at the normal speaking rate. Audio is generated once with the account-free `edge-tts` build tool and stored in the project. The deployed website never contacts a text-to-speech service.

## Scope

This change applies only to Custom Test for both Words and Phrases. Regular quizzes, phrase quizzes, skip quizzes, unit finals, and Review retain their existing question types and scoring behavior.

The existing Multiple Choice, Pinyin input, and Definition options remain unchanged. Listening appears as a fourth option in the same white, black-outlined format panel and is selected by default.

## Audio Assets and Generation

### Source and voice

The build-time generator uses the `edge-tts` Python package and the `zh-CN-XiaoxiaoNeural` voice with rate `+0%`, volume `+0%`, and pitch `+0Hz`. Each request contains exactly the character or phrase that the learner must identify. This guarantees a consistent voice and speaking style across Words and Phrases.

Because the unofficial Edge speech endpoint does not accept custom pronunciation SSML, isolated polyphonic characters use the voice model's default reading. The generated manifest retains the curriculum pinyin beside every asset so known pronunciation mismatches can be identified and regenerated by a future supported method without changing runtime quiz code.

### File layout

The generator writes one MP3 per curriculum item:

```text
audio/
  words/
    0000.mp3
    0001.mp3
    ...
    0999.mp3
  phrases/
    0000.mp3
    0001.mp3
    ...
    0999.mp3
listening-audio-manifest.js
```

Indexes are the same global, zero-based indexes already used by Custom Test. Four-digit names keep lexical and numeric order aligned for the current 1,000-item collections.

`listening-audio-manifest.js` defines `window.CHINESE_READER_LISTENING_AUDIO`. It contains the generator version, voice settings, and aligned `words` and `phrases` arrays. Each entry records the displayed text, curriculum pinyin, and relative MP3 path. The manifest is loaded only by `custom-quiz.html`.

### Generator behavior

`generate-listening-audio.py` reads the aligned `Characters/` + `Pinyin/` and `Phrases/` + `PPinyin/` source files rather than duplicating curriculum arrays. It validates that every current unit contains exactly 100 aligned entries and that each word or phrase is unique across its collection.

Generation is resumable. An existing nonempty MP3 is skipped only when its manifest entry still matches the source text, pinyin, voice, rate, volume, pitch, and generator version. Changed or missing entries are regenerated. Requests use bounded concurrency and retry temporary network or rate-limit failures with backoff. A partially failed run exits nonzero and leaves completed valid files intact for the next run.

The generator writes the manifest only after validating every required file. The build dependency is not loaded by the website and no virtual environment or credential is committed.

## Custom Test Selection UI

`custom-test.html` adds a fourth checkbox row labeled exactly `Listening` beneath Definition. It uses the existing `.format-checkbox`, `.format-checkbox-box`, and `.format-checkbox-label` styling.

`select.js` maintains a `listeningSelected` boolean alongside the three existing format booleans. It defaults to `true`, toggles from the new checkbox, and saves to content-specific local-storage keys:

- Words: `worksheetListening`
- Phrases: `phraseCustomTestListening`

`progress-backup.js` includes both keys so console progress backups preserve the Custom Test format settings.

For every selected word or phrase, `startCustomQuizPage()` adds one `listening` question when the corresponding Listening setting is enabled. Listening questions participate in the same final shuffle as the other chosen formats.

## Listening Question Presentation

Listening uses the existing non-multiple-choice square position and visual proportions.

Before reveal:

- The square is white with the normal black outline.
- It contains `Click to reveal` in black Times New Roman, fitted within the square.
- The typing input is hidden.
- A black button labeled `Play Sound` appears below the square around the normal typing-input area.
- The matching recording is preloaded through an `Audio` object and playback is attempted as soon as the question becomes current.

After reveal:

- The square displays the character or phrase in the existing Chinese display font.
- The Play Sound button remains available.
- Clicking the revealed character or phrase opens the existing details popup with the character or phrase, pinyin, definition, and examples where applicable.

The square click that reveals the answer must stop propagation so it cannot also advance the question. The square click that opens details must also stop propagation.

## Playback State

A focused `listening-audio.js` controller owns the browser `Audio` instance and exposes preload, play, busy, and cleanup behavior to the quiz runner.

- A listening asset is preloaded when its question is prepared.
- Entering a listening question calls play immediately.
- Clicking Play Sound calls the same playback method.
- While a clip is playing or awaiting its play promise, every additional play request is ignored. Audio never overlaps itself.
- The busy state clears on `ended`, `error`, or a rejected play promise.
- Play Sound clicks stop event propagation so they never reveal or advance a question.
- Moving away from a question cleans up its audio listeners and stops any remaining clip before the next question attempts playback.

Browsers can reject audible autoplay before the learner has interacted with the new document. The runner still attempts immediate playback. If that promise is rejected, the question remains usable and Play Sound provides the required fallback. Once the learner uses Play Sound, later questions continue attempting automatic playback normally.

If an MP3 cannot be loaded, the Play Sound button remains visible and changes to `Sound unavailable` for that question. Reveal and advance behavior remain available so the quiz cannot deadlock.

## Reveal, Details, and Advance State

A listening question begins in `concealed` state. Clicking inside the square changes it to `revealed` and redraws without recording any result.

While concealed, keyboard and document-level click handlers do not advance the question. After reveal:

- Any non-repeating key advances to the next question unless the details popup is open.
- A click outside the character square advances.
- Clicking the Play Sound button replays instead of advancing.
- Clicking the character square opens details instead of advancing.
- Clicking within the details popup follows the popup's existing behavior and does not advance.

The normal slide animation is retained between questions. The question is treated as complete for navigation only; it is not inserted into correct or missed collections, does not increment word or phrase progress, and does not call either targeted-knowledge adjustment function.

Finishing a Custom Test containing only Listening questions returns to the appropriate Words or Phrases page without showing a missed-items page.

## Runtime Boundaries

The audio controller is independent of question drawing and curriculum data. It consumes only an audio URL and browser-compatible `Audio` constructor, which makes the replay lock and error state testable without a canvas.

The generated manifest is the only mapping from curriculum items to audio paths. `quiz-engine.js` consumes this mapping and does not duplicate character, phrase, or pinyin arrays.

If the manifest or required entry is missing, Custom Test throws a clear initialization error when Listening is enabled rather than silently sending network requests or synthesizing speech at runtime.

## Testing and Verification

Automated tests cover:

- Listening checkbox markup, default state, toggle state, and Words/Phrases storage keys.
- Progress-backup inclusion of both Listening settings.
- Custom question generation for words and phrases, including mixed question types.
- Listening questions remaining absent from correct, missed, progress, and targeted-knowledge updates.
- Concealed-to-revealed transition and guarded advance behavior.
- Details popup routing after reveal.
- Automatic playback attempt, manual replay, busy-request rejection, ended/error cleanup, and autoplay-rejection fallback.
- Manifest alignment with all current word and phrase runtime data.
- Exactly 1,000 nonempty word MP3s and 1,000 nonempty phrase MP3s.
- MP3 decodability through `ffprobe` and consistent audio codec/sample metadata.
- JavaScript and Python syntax checks.

Browser verification exercises both Words and Phrases Custom Test with Listening alone and mixed with another format. It confirms immediate playback where browser policy allows it, Play Sound fallback, no overlapping replay, reveal typography, details popup behavior, outside-click/key advance, and absence of progress/knowledge mutations.

## Documentation

`AGENTS.md` documents the audio source, consistent voice, generator command, manifest/file layout, local-storage keys, honor-system semantics, and the requirement to regenerate and validate audio whenever word or phrase curriculum text changes.

The documentation identifies `edge-tts` as an unofficial build-time tool. No Edge endpoint call is made by the deployed website.
